## 1. Цель и итог курса

Начальная задача — заново пройти деплой Todo на чистой Ubuntu, заменить Python на Go, SQLite на полноценный PostgreSQL, ручную установку окружения на Docker, а GitHub Actions на Jenkins. React-фронтенд сохранён и включён в процесс выпуска.

В результате получился стенд с двумя VM. На первой работают Nginx с React, Go API и PostgreSQL. На второй расположены контроллер Jenkins и агент сборки. Исходники находятся в GitHub, образы приложения публикуются в GitHub Container Registry, затем скачиваются сервером приложения. Jenkins выполняет проверки, миграции и активацию выпусков.

Практически проверены ручной и автоматический деплой, откат frontend и backend, восстановление базы из резервной копии, совместимость старого кода с новой схемой и автоматический запуск после перезагрузки.

По решению пользователя курс завершён. Автоматические бэкапы были предложены как следующая тема и отложены. Отчёт фиксирует пройденное обучение и существующие ограничения.

## 2. От предыдущего курса к новой архитектуре

В прошлом курсе приложение работало как FastAPI/Uvicorn, React и SQLite. Backend доставлялся архивом исходников. Ubuntu создавала `.venv`, устанавливала Python-зависимости и запускала процесс через `systemd`. Каталоги релизов выбирались ссылкой `current`. GitHub Actions выполнял CI/CD.

| Вопрос | Предыдущий курс | Этот курс |
|---|---|---|
| Backend | Python, FastAPI, Uvicorn | Go, стандартный HTTP-сервер, pgx |
| Что доставляем | Исходники и статику | Собранные Docker-образы |
| Окружение backend | Python и `.venv` на VM | Бинарник внутри образа |
| База | Файл SQLite | Отдельный PostgreSQL-сервис |
| Данные | Каталог на VM | Docker-том PostgreSQL |
| Управление процессом приложения | `systemd` | Docker Engine и restart policy |
| Описание нескольких сервисов | Отдельные настройки служб | `compose.yaml` |
| CI/CD | GitHub Actions | Jenkins controller и agent |
| Выбор версии | Ссылка `current` | Теги образов и `.env` |
| Доставка финального варианта | Архивы по SSH | Registry push/pull |
| Откат | Переключение ссылки и restart | Возврат тега и пересоздание контейнера |

Изменения происходили постепенно. Сначала Go запускался обычным процессом, а PostgreSQL уже жил в Docker. Затем в контейнеры перенесли API и Nginx. После ручного выпуска эту последовательность автоматизировали в Jenkins.

Docker отвечает за упаковку и запуск приложения. Jenkins координирует команды выпуска. Nginx принимает HTTP-запросы. PostgreSQL хранит данные. Каждая из этих задач сохранилась в новой архитектуре.

## 5. Подготовка Ubuntu и SSH

Первый осмотр VM выполняли командами `whoami`, `hostname`, `cat /etc/os-release`, `uname -m`, `nproc`, `free -h`, `df -h /`, `ss -lnt`.

Они отвечают на разные вопросы. Имя пользователя определяет текущие права, hostname различает VM, архитектура влияет на бинарник и образ, а память и диск помогают оценить доступные ресурсы. `ss` показывает слушающие сокеты.

Создание обычного пользователя под root выглядело так:

```bash
adduser devops
usermod -aG sudo devops
install -d -m 700 -o devops -g devops /home/devops/.ssh
```

В `authorized_keys` добавляли публичный ключ с Mac. Каталог `.ssh` получил права 700, файл ключей — 600. Закрытый ключ оставался на клиенте.

`usermod -aG sudo` добавляет группу к существующим. Новая SSH-сессия получает обновлённое членство. В первом упражнении `id -nG` показал отсутствие `sudo`, поэтому повышение прав не работало. После корректировки и повторного входа `sudo whoami` вернул `root`.

SSH проверяет две стороны. Личный ключ клиента подтверждает право входа под пользователем. Ключ хоста подтверждает, к какому серверу подключается клиент. При автоматизации это разделение сохранилось в `todo-deploy-ssh` и `todo_known_hosts`.

## 6. Go и первый деплой бинарника

Первый Go-сервис отвечал на `GET /api/health` значением `{"status":"ok"}`. Сначала его запустили на Mac через `go run .`, затем собрали для Ubuntu.

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -o /tmp/todo-api-linux-amd64 .
```

- `GOOS=linux` задаёт целевую ОС.
- `GOARCH=amd64` соответствует `x86_64` сервера.
- `CGO_ENABLED=0` отключает использование CGo для этой сборки.
- `-o` задаёт имя результата.
- `.` выбирает текущий пакет.

Mac был ARM, поэтому бинарник для него и бинарник для Ubuntu имели разные платформы. Команда `file` показала Linux ELF x86-64.

Бинарник передали через `scp`, выдали право выполнения и запустили в SSH-сессии. На Ubuntu `curl http://127.0.0.1:8000/api/health` вернул 200, а `ss` показал `127.0.0.1:8000`.

Эта практика связала два способа деплоя. Для Python на сервере требовались интерпретатор и зависимости. Наш Go backend собирался в файл, который можно было перенести и запустить. Позже тот же файл поместили в Docker-образ.

## 7. Docker, образы и контейнеры

Docker Engine установили на обеих VM из официального APT-репозитория Docker для Ubuntu `resolute`. Установленный набор включал `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`.

Ключ репозитория использовался APT для проверки подписей. `systemctl is-active docker` подтвердил работу службы. `docker run --rm hello-world` проверил обращение CLI к Engine, скачивание образа и запуск контейнера.

Основные понятия курса:

| Объект | Назначение |
|---|---|
| Dockerfile | Последовательность сборки образа |
| Образ | Файловые слои, конфигурация и команда запуска |

## 8. Первый PostgreSQL

Сначала Compose содержал только сервис `db` из официального образа `postgres:17`. Создали базу `todo`, роль `todo` и отдельный именованный том `postgres_data`.

Пароль генерировался на сервере и сохранялся в `.env` с правами 600. Значение не добавляли в Git. Переменные `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` используются образом для первичной инициализации пустого каталога данных. Изменение пароля в `.env` при существующем томе само по себе не меняет пароль роли внутри PostgreSQL.

Первое подключение проверили командой:

```bash
sudo docker compose exec db sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" psql -h 127.0.0.1 -U todo -d todo -c "SELECT current_database(), current_user;"'
```

Получили `todo` в обоих столбцах. На этом этапе клиент `psql` находился в контейнере. Затем Go на хосте подключался через опубликованный `127.0.0.1:5432`.

Итоговый том называется `docker-jenkins_postgres_data` и подключён к `/var/lib/postgresql/data`. Мы проверили это через `docker inspect` раздела Mounts. Имя проекта и имя тома позволили пересоздать контейнер базы с прежними данными.

Роль `todo`, созданная через `POSTGRES_USER`, является начальной административной ролью образа. Разделение роли миграций и ограниченной runtime-роли в курсе не выполнялось.

## 9. Go API и подключение к базе

Backend использует стандартную библиотеку `net/http`, `encoding/json` и драйвер `pgx/v5`. `pgxpool` управляет пулом соединений. При запуске приложение требует `DATABASE_URL`, создаёт пул и проверяет подключение с таймаутом 10 секунд.

Переменная `HTTP_ADDR` задаёт адрес прослушивания. Без неё приложение использует `127.0.0.1:8000`. В контейнере установлено `0.0.0.0:8000`, чтобы запросы могли приходить от Nginx по сети контейнеров.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Проверка связи API с PostgreSQL |
| GET | `/api/version` | Версия, встроенная в Go-бинарник |
| GET | `/api/todos` | Список задач, новые по id первыми |
| POST | `/api/todos` | Создание задачи, статус 201 |
| PATCH | `/api/todos/{id}` | Изменение признака done |
| DELETE | `/api/todos/{id}` | Удаление, статус 204 |

Название обрезается по краям и проверяется на длину от 1 до 200 Unicode-символов. Изменение и удаление отсутствующей задачи возвращают 404. SQL-параметры передаются через `$1`, `$2`. Создание и изменение возвращают данные через `RETURNING`.

Позже в структуру `todo` добавили `CreatedAt time.Time` с JSON-именем `created_at`. Обновили SELECT, RETURNING и Scan, чтобы количество и порядок полей совпадали.

`/api/health` проверяет Ping базы. Успех health endpoint не доказывает наличие всех столбцов таблицы или корректность каждого CRUD-запроса. Чтение задач и действия через браузер проверялись отдельно.

## 10. Сборка Go-образа

В `backend/Dockerfile` две стадии.

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.26-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY *.go ./
ARG TARGETOS
ARG TARGETARCH
ARG RELEASE=development
RUN CGO_ENABLED=0 GOOS="$TARGETOS" GOARCH="$TARGETARCH" \
    go build -p 1 -trimpath \
    -ldflags="-X main.version=$RELEASE" \
    -o /todo-api .

FROM scratch
COPY --from=build /todo-api /todo-api
USER 65532:65532
ENTRYPOINT ["/todo-api"]
```

Первая стадия содержит компилятор. Сначала копируются `go.mod`, `go.sum` и скачиваются зависимости. Затем копируются исходники. Такой порядок помогает использовать кеш зависимостей при изменении кода.

`BUILDPLATFORM` выбирает платформу выполнения инструментов сборки. `TARGETOS` и `TARGETARCH` задают платформу результата. `--platform linux/amd64` в команде Buildx выбирает целевую платформу VM приложения.

`-p 1` добавили после OOM на VM Jenkins для ограничения числа одновременно собираемых пакетов. `-trimpath` убирает локальные пути сборки из результата. `-ldflags` записывает строку выпуска в `main.version`.

Финальная стадия `scratch` получает только бинарник. В ней отсутствуют shell и curl, поэтому диагностику через такие инструменты выполняют снаружи или отдельным контейнером. Наш runtime использует PostgreSQL по внутренней сети с `sslmode=disable`. Включение TLS для внешних сервисов потребовало бы отдельно учесть CA-сертификаты внутри runtime-образа.

Пример сборки на Mac:

```bash
docker buildx build --platform linux/amd64 --load \
  --build-arg RELEASE=lesson-check \
  -t todo-api:lesson-check backend
```

`--load` помещает результат в локальное хранилище Engine. Версию определяет собранный код. Смена `.env` без замены контейнера не заставит старый процесс сообщать новый выпуск.

## 11. Сборка React и Nginx

React-фронтенд сохранён из прошлого проекта. Первая стадия его Dockerfile использует Node.js, устанавливает зависимости через `npm ci` и выполняет `npm run build`. В `dist` появляются HTML, JavaScript и CSS.

Аргумент `RELEASE` создаёт `dist/release.txt`. Вторая стадия на основе `nginx:stable-alpine` получает собранные файлы и `nginx.conf`.

Браузер выполняет React-код после загрузки JS. На сервере готовую статику отдаёт Nginx. Vite-прокси нужен для локального dev-режима, а production-проксирование описано в Nginx.

```nginx
location /api/ {
    resolver 127.0.0.11 valid=10s ipv6=off;
    set $api http://api:8000;
    proxy_pass $api;
}

location / {
    try_files $uri $uri/ /index.html;
}
```

Имя `api` разрешается встроенным DNS Docker. Resolver и переменная позволяют Nginx повторно разрешать имя после пересоздания API и смены его IP. Путь `/api/...` передаётся backend. `try_files` возвращает `index.html` для клиентских маршрутов SPA.

Проверяли файлы временным контейнером с заменой entrypoint на `ls`. Видели `index.html`, `assets/*.js`, `assets/*.css`, а также `50x.html` базового Nginx. Команда `nginx -g 'daemon off;'` держит основной процесс на переднем плане для Docker.

## 12. Сети, порты и Compose

Итоговый `compose.yaml` описывает проект `docker-jenkins` и три сервиса `db`, `api`, `web`.

```text
Браузер → VM:80 → web:80 → api:8000 → db:5432
                              PostgreSQL → postgres_data
```

Публично опубликован Nginx. API и PostgreSQL доступны внутри сети Compose. Строка `5432/tcp` в `docker compose ps` сама по себе не означает публикацию порта на хосте. Публикация содержит отображение адреса и порта, например `127.0.0.1:8080->80/tcp`.

У слова localhost всегда есть контекст. `127.0.0.1` на Mac указывает на Mac, в SSH-сессии — на VM, внутри контейнера — на этот контейнер. Поэтому после контейнеризации Go адрес базы изменился с `127.0.0.1:5432` на `db:5432`.

Сейчас `web` публикует оба правила:

```yaml
ports:
  - "80:80"
  - "127.0.0.1:8080:80"
```

Первое открывает HTTP по IP, второе обслуживает локальные проверки скриптов и туннель.

API зависит от `db` с условием `service_healthy`. Healthcheck использует `pg_isready`. У `web` обычный `depends_on: api`, который задаёт порядок старта, но не доказывает HTTP-готовность API. После запуска сеть и приложение проверяются с повторами.

`.env` на VM содержит пароль и выбранные версии. Концептуальный пример с вымышленным паролем:

```dotenv
POSTGRES_PASSWORD=GENERATED_SERVER_PASSWORD
API_TAG=jenkins-42
WEB_TAG=jenkins-42
```

`API_TAG` и `WEB_TAG` независимы. Compose подставляет их в полные имена GHCR. Дефолт `lesson-5` сохранён в YAML, но образ с этим тегом в GHCR в курсе не публиковали. Для рабочего запуска нужны реальные значения в `.env`.

Полезные проверки — `docker compose config --quiet`, `--images`, `--volumes`. Полный `config` может вывести подставленный пароль, поэтому в чат передавались выборочные результаты.

## 13. Доставка образов архивами

## 14. SSH-туннели

Для Todo на Mac открывали:

```bash
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 \
  devops@177.203.59.227
```

Браузер обращался к `http://127.0.0.1:18080/`. Левая пара адреса и порта принадлежит Mac, правая разрешается со стороны SSH-сервера. `-N` оставляет только перенаправление без удалённой оболочки. `Ctrl+C` закрывает туннель.

Для Jenkins используется тот же принцип:

```bash
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:19090:127.0.0.1:8080 \
  devops@IP_СЕРВЕРА_JENKINS
```

Интерфейс доступен на `http://127.0.0.1:19090/`. Jenkins публикует порт только на loopback своей VM. После перезагрузки SSH-туннель требуется открыть заново.

## 19. Отдельный агент и systemd

На VM Jenkins создали пользователя `jenkins-agent` и каталог `/home/jenkins-agent/agent`. Java 21 установили на хосте отдельно от Java внутри контейнера Jenkins.

В UI зарегистрировали Permanent Agent `docker-builder`, label `docker-builder`, один executor и remote root directory агента. Pipeline перевели на:

```groovy
agent {
    label 'docker-builder'
}
```

`agent.jar` скачали с нашего контроллера. Секрет узла записали в `agent.secret` под владельцем агента. Подключение использовало WebSocket через `http://127.0.0.1:8080/`, поэтому отдельный входящий порт 50000 не понадобился.

```text
/usr/bin/java -Djava.io.tmpdir=/home/jenkins-agent/agent/tmp -jar /home/jenkins-agent/agent/agent.jar -url http://127.0.0.1:8080/ -name docker-builder -secret @/home/jenkins-agent/agent/agent.secret -webSocket -workDir /home/jenkins-agent/agent
```

Параметр `-Djava.io.tmpdir` должен находиться до `-jar`. Служба `/etc/systemd/system/jenkins-agent.service` запускается как `jenkins-agent`, использует `Restart=always`, `RestartSec=10`, `UMask=0077`, включена через `systemctl enable`.

## 22. Скрипты выпуска и автоматический откат

`scripts/deploy-web.sh` и `scripts/deploy-api.sh` принимают тег вида `jenkins-N` и второй аргумент `true` или `false` для учебного сбоя.

Порядок выполнения:

1. Проверка аргументов.
2. Общая блокировка `.deploy.lock` через `flock -n`.
3. Чтение предыдущего API_TAG или WEB_TAG из `.env`.
4. HTTP-проверка предыдущего выпуска.
5. Копия `.env` и подготовка временного файла с новым тегом.
6. Включение флага `rollback_needed` и замена `.env`.
7. Compose pull выбранного сервиса.
8. Compose up только этого сервиса.
9. Healthcheck и проверка версии.
10. При `true` — намеренная ошибка.
11. После полного успеха отключение флага отката.

Обработчик `trap ... EXIT` при ошибке восстанавливает прежний `.env`, пересоздаёт сервис из предыдущего локального образа и проверяет версию. Даже после успешного восстановления результат нового выпуска остаётся неуспешным.

Общая блокировка нужна, потому что оба скрипта заменяют один `.env`. В Jenkins дополнительно включили `disableConcurrentBuilds()`, чтобы два запуска задания не пересекались при доставке и активации файлов.

Скрипты сначала существовали только на сервере. Затем перенесли их в Git. Jenkins проверяет Bash-синтаксис, передаёт файл как `.next`, проверяет на сервере, выставляет права и заменяет рабочий скрипт через `mv`.

Фронтенд проверяется через `release.txt`, backend через JSON `/api/version`. Backend сейчас сравнивает JSON как точную строку ожидаемого формата. Изменение порядка или форматирования JSON потребовало бы обновления этой проверки.

HTTP-повторы восстанавливаются после временных 502, Empty reply и Connection reset во время пересоздания контейнеров. При несовпадении успешно прочитанной версии скрипт сразу считает выпуск неуспешным.

Подтверждённые упражнения включали frontend 19 → возврат к 18, backend 31 → возврат к 30, а также откаты после перехода на GHCR. При сбое backend последующие стадии frontend пропускаются. При сбое frontend уже успешно выпущенный backend остаётся новой версии.

## 25. Бэкап и восстановление PostgreSQL

Перед изменением схемы создали задачу, сделали custom-format архив через `pg_dump -Fc` и восстановили его в отдельную базу. После копирования добавили новую задачу и убедились, что восстановленная база её не содержит.

Рабочая процедура на VM приложения:

```bash
cd ~/docker-jenkins
mkdir -p backups
chmod 700 backups
sudo -v
backup="backups/todo-$(date -u +%Y%m%dT%H%M%SZ).dump"
(umask 077; sudo -n timeout 30s docker compose exec -T db pg_dump -w -U todo -d todo -Fc </dev/null > "$backup") && ls -lh "$backup"
```

Для маленькой учебной базы получили архив около 2,3 КБ. Код завершения 0 подтверждает успех команды, а пригодность файла проверяется восстановлением.

- `-Fc` создаёт custom archive для `pg_restore`.
- `-T` отключает терминал при Docker exec.
- `-w` запрещает pg_dump ждать ввода пароля.
- `</dev/null` закрывает stdin.
- `timeout 30s` ограничивает длительность учебной операции. Для большой базы срок нужно выбирать по её объёму.
- `umask 077` ограничивает доступ к файлу владельцем.

`pg_dump` получает согласованный снимок базы при её работе. Выгрузка через используемую роль предназначена для данных и структуры базы. Полное восстановление инфраструктуры, ролей кластера и конфигурации сервера является отдельной задачей.

Восстановление проверяли так:

```bash
sudo docker compose exec -T db createdb -U todo -O todo todo_restore_check </dev/null
sudo docker compose exec -T db pg_restore -w -U todo -d todo_restore_check --exit-on-error --single-transaction < "$backup"
sudo docker compose exec -T db psql -U todo -d todo_restore_check -c 'SELECT id, title, done FROM todos ORDER BY id;' </dev/null
```

Архив на stdin нужен `pg_restore`, поэтому для этой операции вместо `/dev/null` передаётся файл.

Копию `todo-20261107T212447Z.dump` скачали в `~/todo-backups/` на Mac. `shasum -a 256` на Mac и `sha256sum` на Ubuntu дали одинаковый результат. Хеш проверяет совпадение переданного файла, а восстановление проверяет его содержимое.

Ручная копия вне VM и restore-check выполнены. Расписание, ротация и автоматическая доставка резервных копий отложены по решению пользователя. Тестовые базы `todo_restore_check` и `todo_migrations_check` создавались внутри того же PostgreSQL. Их последующее удаление в курсе не зафиксировано.

## 26. Миграции и совместимость версий

### 001 — создание таблицы

```sql
CREATE TABLE IF NOT EXISTS todos (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200),
    done boolean NOT NULL DEFAULT false
);
```

### 002 — время создания

```sql
ALTER TABLE todos
    ADD COLUMN created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP;
```

Сначала применили схему на сервере, затем обновили Go. Старый код явно перечисляет используемые поля и при INSERT не передаёт created_at. PostgreSQL заполняет его через DEFAULT.

Существующие строки получили время миграции. Восстановить реальное время их создания по старой схеме было невозможно. Новые задачи получают время вставки в транзакции PostgreSQL.

Проверка совместимости включала запуск старого `jenkins-30` на расширенной схеме. Через старый API создали задачу «старое апи», затем вернули новый код и увидели created_at у этой задачи.

Такой порядок позволяет подготовить расширение схемы, выпустить использующий его код и при необходимости вернуть старый код. Удаление или переименование используемого столбца потребовало бы другой последовательности с промежуточной совместимостью.

### 003 — частичный индекс

```sql
CREATE INDEX todos_pending_id_idx
    ON todos (id DESC)
    WHERE done = false;
```

Индекс содержит невыполненные задачи и соответствует запросу с `WHERE done = false ORDER BY id DESC`. Текущий API получает все задачи, поэтому изменение было упражнением на автоматическую миграцию. Ускорение текущего запроса этой практикой не подтверждалось.

Обычный CREATE INDEX во время построения ограничивает конкурирующие записи в таблицу. На маленьком стенде это допустили. CREATE INDEX CONCURRENTLY имеет другие ограничения и не подходит внутрь нашего общего транзакционного запуска.

## 27. Учёт миграций и транзакции

Первые две миграции уже выполнили вручную. После просмотра `\d todos` зарегистрировали baseline в таблице:

```sql
CREATE TABLE schema_migrations (
    version text PRIMARY KEY,
    applied_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

В неё записали имена `001_create_todos.sql` и `002_add_created_at.sql`. Время этих baseline-записей означает время регистрации истории.

Запускатор `scripts/migrate.sh DATABASE_NAME` вычисляет корень относительно собственного пути, собирает временный SQL-файл и передаёт его `psql`. Миграции читаются из `backend/migrations/*.sql`. Имена проверяются по шаблону из трёх цифр и буквенно-цифрового имени.

Внутри SQL сначала устанавливается `lock_timeout = '15s'` и берётся `pg_advisory_xact_lock(817204631)`. Это транзакционная блокировка с выбранным постоянным ключом. Она координирует другие запуски того же мигратора в этой базе, но не блокирует автоматически любые административные SQL-команды.

Для каждого файла psql проверяет EXISTS в `schema_migrations`, сохраняет результат через `\gset` и использует `\if`. Уже известный файл пропускается. Новый выполняется и регистрируется в истории.

Опции psql имеют отдельный смысл:

- `-X` исключает пользовательский psqlrc.
- `-w` запрещает ожидание пароля.
- `ON_ERROR_STOP=1` останавливает скрипт при SQL-ошибке.
- `--single-transaction` выполняет весь комплект ожидающих миграций и историю одной транзакцией.

У миграций убрали собственные BEGIN/COMMIT, чтобы транзакцией управлял один уровень.

На пустой `todo_migrations_check` первый запуск вывел Applying 001/002, второй Skipping 001/002. Затем временная 003 добавляла migration_probe и обращалась к отсутствующей таблице. После ошибки колонка отсутствовала и запись 003 в истории отсутствовала. Учебный ошибочный файл удалили.

Это подтвердило атомарность изменений. Учёт пока выполняется по имени файла. Контрольные суммы содержимого, проверка неожиданного порядка истории и автоматические down-миграции не реализованы. Применённые миграции следует сохранять как историю, новые изменения оформлять следующим файлом.

## 28. Миграции в Pipeline

В CI ручные вызовы двух SQL-файлов заменили на:

```bash
COMPOSE_FILE=compose.ci.yaml bash scripts/migrate.sh todo
COMPOSE_FILE=compose.ci.yaml bash scripts/migrate.sh todo
```

В production потребовался режим `MIGRATION_USE_SUDO=true`. Он использует точный Compose-путь и разрешённую через sudoers команду psql. Сам Bash-скрипт и файлы читаются под `devops`.

Стадия `Apply database migrations` упаковывает запускатор и `backend/migrations` в архив `migrations-jenkins-N.tar.gz`, доставляет его и распаковывает в:

```text
/home/devops/docker-jenkins/migration-releases/jenkins-N/
  scripts/migrate.sh
  backend/migrations/*.sql
```

Так сохраняется комплект конкретной сборки. Старый скрипт в корневом `scripts/` может читать более ранний набор, поэтому для повторения использовали путь комплекта выпуска, например `migration-releases/jenkins-35/scripts/migrate.sh`.

Серверный вызов защищён общей `.deploy.lock`. Затем запускается мигратор. Если он завершится ошибкой, SSH и стадия вернут ненулевой код, Activate backend будет пропущена.

В выпуске 35 production пропустил 001 и 002, применил 003, создал индекс и добавил строку истории. Наличие индекса проверили через `\di todos_pending_id_idx`. Повторный запуск пропустил все три миграции.

Миграции и активация API выполняются отдельными операциями. После успешной миграции и неудачного выпуска кода схема остаётся новой. Поэтому совместимость со старым приложением требуется заранее.

## 29. GHCR вместо архивов

### Устройство доставки

Финальные имена образов:

```text
ghcr.io/kinzaz/todo-web:jenkins-N
ghcr.io/kinzaz/todo-api:jenkins-N
```

Jenkins собирает и проверяет локальный образ. `docker tag` добавляет ему имя registry, `docker push` публикует слои и манифест, а `docker pull` скачивает их на другой сервер. Общие слои переиспользуются, что наблюдали в строках Already exists.

Digest идентифицирует содержимое манифеста. В одной сборке индекс и платформенный манифест имеют разные digest. Поскольку мы публиковали одну платформу, сравнивали digest результата push и соответствующего pull.

Подтверждённые публикации:

| Образ | Digest |
|---|---|
| todo-web:jenkins-39 | `sha256:71968f363b0ba228a59e45e6e965ddbbd4195866f28d8b513ffda200b07da94c` |
| todo-api:jenkins-41 | `sha256:51489615a281cd70b44e92b22d0777bc4d3686f8415e93c4afc7135868767fc6` |

Это исторические проверенные выпуски, а не утверждение о текущей версии на сервере.

### Авторизация

Для Jenkins создали GitHub Personal Access Token classic с `write:packages` и сохранили его в Jenkins Credentials `ghcr-push` типа Username with password. Username — `kinzaz`, Password — токен.

Для VM приложения использовали отдельный classic-токен `read:packages` и выполнили `sudo docker login`. Его конфигурация Docker сохраняется под root, поскольку production-команды используют sudo.

В Pipeline логин выполняется через `printf ... | docker login --password-stdin`. `set +x` отключает трассировку команд с секретом. Временный `DOCKER_CONFIG` создаётся через mktemp и удаляется после блока. Предупреждение про незашифрованный config.json относится к этому временному файлу. На production логин сохранён дольше и требует соответствующего отношения к root-конфигурации Docker.

При первом создании пакеты приватны. Проверяли пакет `todo-web` в профиле GitHub.

### Ошибки публикации

Сначала был ошибочно выбран fine-grained токен. В его интерфейсе отсутствовало нужное classic scope `write:packages`. После открытия Tokens (classic) создали подходящий токен и обновили Credentials.

Затем login проходил, слои загружались, но публикация завершалась denied. В GHCR появился пакет без нужного тега, с манифестом attestation. Публикация через `docker push --platform linux/amd64` успешно создала тег. Это проверенный обход проблемы для данного стенда. Точная причина отказа полного набора манифестов не была установлена.

Параметр публикует платформенный образ без общего индекса и связанных attestations. Его последствия обсуждались при исправлении.

### Переход сервера приложения

Перед сменой имени в Compose текущему короткому локальному образу добавили GHCR-имя через docker tag. Это сохранило возможность локального отката к предыдущему выпуску.

Затем `image` заменили на полные GHCR-имена, в deploy-скрипты добавили Compose pull после записи нового тега, а архивные стадии Deliver/Load images удалили из Pipeline.

Теперь по SSH передаются скрипты и SQL-комплекты. Образы приложение получает из registry.

## 30. Конечная цепочка выпуска

Порядок стадий текущего Jenkinsfile при подготовке отчёта:

| Стадия | Что выполняет |
|---|---|
| Declarative Checkout SCM | Автоматически получает исходники выбранного коммита |
| Inspect environment | Выводит пользователя, workspace, SHA и создаёт report.txt |
| Check Docker | Проверяет доступ агента к Engine и Buildx |
| Check registry access | Проверяет вход в GHCR |
| Build frontend image | Собирает React/Nginx и release.txt |
| Check frontend image | Проверяет статику и nginx -t |
| Publish frontend image | Публикует frontend в GHCR |
| Check deployment access | Проверяет SSH на VM приложения |
| Build backend image | Собирает Go с версией |
| Check backend image | Поднимает CI PostgreSQL, мигрирует и проверяет API |
| Publish backend image | Публикует Go-образ в GHCR |
| Deliver backend deployment script | Доставляет deploy-api.sh из коммита |
| Apply database migrations | Применяет SQL к базе приложения |
| Activate backend | Скачивает, запускает и проверяет API |
| Deliver deployment script | Доставляет deploy-web.sh из коммита |
| Activate frontend | Скачивает, запускает и проверяет frontend |
| Post Actions | Сохраняет report.txt |

Frontend публикуется до проверки backend. Следовательно, образ frontend может существовать в registry даже при последующем неуспехе всей сборки. Это ещё один пример различия публикации артефакта и его активации на сервере.

Обычный запуск выполняется вручную через Build with Parameters. Оба параметра учебных сбоев должны быть false. Любой ранний сбой останавливает последующие стадии.

Пользовательские запросы после выпуска идут другим путём:

```text
Браузер
  → HTTP 177.203.59.227:80
  → Docker port mapping
  → Nginx web:80
      → статика React
      → /api/ → api:8000
                    → db:5432
                         → том postgres_data
```

Jenkins и GHCR участвуют в доставке выпусков. Обслуживание уже загруженной версии происходит на VM приложения.

## 31. Перезагрузка и публичный доступ

В Compose каждого application-сервиса добавили `restart: unless-stopped`. Docker Engine включён в автозапуск. При штатной перезагрузке VM Docker поднимает контейнеры, а PostgreSQL подключает прежний том.

Restart policy реагирует на завершение контейнера. Healthcheck сам по себе не перезапускает живой процесс, который стал unhealthy. Это разные механизмы.

После перезагрузки VM приложения пользователь получил `{"status":"ok"}` через Nginx. На VM Jenkins контроллеру добавили аналогичную restart policy, агент уже работал через systemd. Проверили Docker, агент, swap и сохранение интерфейса Jenkins после рестарта.

Публичный Todo открыли по IP по решению пользователя. Порт 80 публикуется для внешних запросов, локальный 8080 сохранён для deploy-скриптов. HTTPS для этого нового стенда не настраивали. Авторизация Todo отсутствует, список общий для посетителей.

Jenkins остаётся доступен через SSH-туннель. Это влияет и на триггеры webhook — GitHub не может напрямую обратиться к локальному адресу Mac или loopback VM.

## 32. Визуализация и триггеры Jenkins

### Граф и Stage View

В Jenkins уже был граф через Stages. Он показывает цепочку именованных стадий, время и логи выбранного узла. На общем экране отдельные дорожки соответствуют запускам.

Затем по просьбе пользователя установили Pipeline: Stage View 2.41 и зависимости Pipeline Graph Analysis и Pipeline: REST API. Установка прошла успешно. На Status появилась таблица с прямоугольными блоками и именами из `stage(...)`, слева появился Full Stage View.

Изменений Jenkinsfile для отображения не потребовалось. При новом запуске эта таблица показывает прогресс существующих стадий.

### Кнопка, push и Git-теги

Практически настроен ручной запуск. Другие варианты обсуждались теоретически.

| Событие | Возможный сценарий |
|---|---|
| Нажатие Build | Явный ручной выбор момента выпуска и параметров |
| Push или merge | Автоматические проверки и возможный выпуск окружения |
| Push Git-тега v1.2.0 | Выбор коммита, отмеченного как релиз |
| Ручное одобрение после сборки | Продвижение заранее проверенного артефакта |

Git-тег указывает на коммит. Docker-тег указывает на образ. Автоматизация может связать эти два имени, но это отдельная настройка.

Для обнаружения Git-тегов Jenkins можно настроить Multibranch Pipeline с Discover tags, подходящей стратегией сборки тегов и сканированием или webhook. Само условие `when { tag 'v*' }` фильтрует стадию уже запущенного Pipeline.

У нас Pipeline читает `master`. Обнаружение тегов, GitHub webhook и запуск по тегу в курсе не внедрены. С текущим закрытым сетевым доступом можно было бы использовать периодическое сканирование со стороны Jenkins.

## 33. Разобранные ошибки

### Отсутствие sudo у devops

Признаки — `id -nG` без группы sudo, отказ `sudo whoami`. Исправили членство и вошли заново. Узнали разницу между настройками пользователя и группами уже запущенной сессии.

### Неверная строка DATABASE_URL

В учебной команде перед `${POSTGRES_PASSWORD}` был лишний обратный слеш. Bash передал буквальную строку, Go сообщил invalid database configuration. После удаления экранирования пароль подставился корректно.

### Циклическая зависимость стадий Dockerfile

Buildx показал NoEmptyContinuation и circular dependency detected on stage build. Лишнее продолжение строки нарушило границу RUN/FROM. Восстановили Dockerfile с окончанием `-o /todo-api .` без завершающего обратного слеша.

### Agent.jar отсутствовал

Java выдала Unable to access jarfile. Проверили каталог, повторно скачали agent.jar и запускали по абсолютному пути.

### Узел online, затем offline из-за /tmp

На Ubuntu /tmp находился в tmpfs размером около 948 МиБ, что меньше порога Jenkins в 1 ГиБ. Основной диск имел около 20 ГБ свободного места. Задали агенту `-Djava.io.tmpdir=/home/jenkins-agent/agent/tmp`.

Первое исправление не проявилось, поскольку работали два Java-процесса. Старый ручной агент был подключён с /tmp, служба с новым каталогом пыталась подключиться под тем же именем. Через pgrep нашли оба PID, завершили старый процесс и подтвердили новый java.io.tmpdir через System Information. Узел начал принимать задания.

### OOM при компиляции Go

Pipeline многократно терял агент. Диагностика показала `Out of memory: Killed process ... (java)`, а Docker inspect контроллера — `Status=exited OOMKilled=true`. Агент оставался запущенным и получал Connection refused от контроллера.

Добавили swap 2 ГиБ, сохранили его в fstab, ограничили Go build через `-p 1`, подняли контроллер и повторили новую сборку. Следующий выпуск успешно сообщил jenkins-29.

Свободная память после OOM не опровергает нехватку в прошлом — завершённый процесс уже освободил свою память.

### Нулевые файлы pg_dump и ожидание терминала

Первые попытки дали пустые файлы. PostgreSQL отвечал, блокировок не было, pg_dump в процессах отсутствовал. Проверка версии утилиты с закрытым stdin сработала. Команда с `-w`, `</dev/null` и timeout завершилась кодом 0 и создала архив.

Точная причина первоначального зависания не установлена. Нулевой файл возникал потому, что оболочка создавала его для `>` ещё до успешной записи архива. При повторении используем проверенный вариант команды.

### Permission denied по SSH

Проверили публичный ключ, правильную VM, пользователя, authorized_keys и права. После исправления Jenkins смог выполнить whoami/hostname на сервере приложения.

### GHCR login успешен, push запрещён

Первый токен был fine-grained. Для GHCR в нашем сценарии понадобился classic с write:packages. Затем отдельно решали отказ публикации полного набора манифестов через платформенный push. Успешный login подтверждает вход, а право публикации проверяется самой операцией push.

### Краткие HTTP-ошибки при выпуске

Наблюдали 502, Empty reply from server, Connection reset by peer. Они возникали при пересоздании API или Nginx. Повторы получали ожидаемый результат. Это подтверждает наличие короткой недоступности в выбранной стратегии выпуска.

### Приглашение оболочки и переносы строк

Пустой вывод может означать успех команды или её продолжающееся выполнение. Приглашение `$` означает готовность к следующей команде, `>` — ожидание продолжения незаконченного выражения. Обратный слеш для продолжения должен завершать строку. В проблемном упражнении использовали однострочные команды для исключения ошибок вставки.

## 34. Ограничения и расхождения

### Расхождение текущего frontend push с успешным упражнением

В локальном Jenkinsfile на момент подготовки отчёта стадия Publish frontend image содержит `docker push "$image"`. В успешном упражнении публикации frontend использовался `docker push --platform linux/amd64 "$image"`. Backend в текущем файле содержит платформенный параметр.

Это расхождение зафиксировано по исходникам. При подготовке отчёта код Pipeline не менялся. Если проблема denied полного набора манифестов повторится, проверенный в курсе вариант для frontend — платформенный push. Нельзя считать, что этот параметр уже сохранён в текущем файле.

### Границы автоматизации

- Compose приложения находится в Git, но Pipeline автоматически его на сервер не доставляет. Изменения Compose синхронизировали вручную.
- Подготовка VM, sudoers, служба агента и Compose Jenkins задавались вручную. Полного IaC-описания восстановления нет.
- Автоматическое резервирование базы и Jenkins home отложено. Ручной backup/restore выполнен.
- HTTPS, аутентификация Todo и настроенные оповещения не внедрены.
- Старые образы, архивы и каталоги migration-releases автоматически не очищаются. На дисках ограниченный объём.
- Теги базовых образов подвижны. Повторная сборка одного коммита позже может использовать новые базовые слои.
- В production Compose выбирает образ по тегу. Доставка по digest как обязательное правило не реализована.
- Тесты ограничены smoke-проверками и ручными CRUD-упражнениями.
- В скриптах нет контроля checksum применённых SQL-файлов.
- Временная остановка процесса, SIGKILL, сбой VM или утрата SSH не дают общей гарантии завершения отката.
- При откате скрипт использует предыдущий локальный образ. Его удаление может сделать восстановление невозможным без дополнительного скачивания.
- Скрипт перед выпуском проверяет исходный health/version. При уже сломанном исходном приложении обычный путь выпуска остановится до переключения, и может потребоваться отдельная восстановительная операция.
- Код мигрируется отдельно от приложения. Возврат кода не отменяет SQL, пользовательские действия и новые данные.
- API и frontend откатываются независимо. Единый атомарный релиз обоих компонентов не реализован.
- Все ожидающие миграции выполняются одной транзакцией. Миграции с операциями, запрещёнными внутри транзакции, требуют другого механизма.
- Существование root-owned или административных сервисов и прав на файлы не заменяет отдельной модели минимальных полномочий.

### Последнее подтверждённое состояние

В курсе явно наблюдали API и frontend в GHCR-образах jenkins-42. Пользователь затем сообщил успешный учебный откат API, после чего отдельно проверяли перезагрузки и порт 80. Последующие HTTP-версии после каждого административного шага в чате фиксировались не всегда.

Текущий запуск определяется запросами `/api/version`, `/release.txt` и `docker compose ps`. Номер последнего build в Jenkins может отличаться от версии приложения после отката.

Ресурсы VM и версии внешних сервисов в этом документе являются историческими наблюдениями курса. Секреты, пароли, токены и закрытые ключи в отчёт не включены.

```bash
cd ~/docker-jenkins
```

`/api/todos` содержит пользовательские данные. Его можно применять для собственной диагностики, учитывая содержимое перед передачей вывода другим.

```bash
sudo docker compose exec -T db psql -U todo -d todo -c '\d todos' </dev/null
sudo docker compose exec -T db psql -U todo -d todo -c 'SELECT version, applied_at FROM schema_migrations ORDER BY version;' </dev/null
sudo docker inspect docker-jenkins-db-1 --format '{{range .Mounts}}{{println .Name "->" .Destination}}{{end}}'
```

### На VM Jenkins — диагностика

```bash
cd ~/jenkins
sudo docker compose ps
sudo docker compose logs --tail=50 jenkins
sudo systemctl status jenkins-agent --no-pager -l
sudo journalctl -u jenkins-agent -n 50 --no-pager -l
pgrep -u jenkins-agent -a java
free -h
swapon --show
sudo df -h / /tmp /home/jenkins-agent/agent/tmp
sudo journalctl -k --since '20 minutes ago' --no-pager | grep -Ei 'oom|out of memory|killed process'
```

При проверке состояния контейнера контроллера:

```bash
sudo docker inspect jenkins-learning-jenkins-1 --format 'Status={{.State.Status}} OOMKilled={{.State.OOMKilled}} Restarts={{.RestartCount}}'
```

### Повторный запуск миграций

Для CI используются COMPOSE_FILE и COMPOSE_PROJECT_NAME. Для сервера приложения выбирается конкретный доставленный комплект:

```bash
MIGRATION_USE_SUDO=true bash migration-releases/jenkins-N/scripts/migrate.sh todo
```

`N` требуется заменить реальным номером каталога. Перед запуском следует понимать, какие новые файлы находятся в этом комплекте.

### Ручной выпуск и откат

```bash
./deploy-api.sh jenkins-N
./deploy-web.sh jenkins-N
```

Команды изменяют рабочий выпуск, используют registry и требуют существующего исходного тега в .env. Для учебного отказа второй аргумент `true`. В обычной эксплуатации он должен отсутствовать или равняться false.
